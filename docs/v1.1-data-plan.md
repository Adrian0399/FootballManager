## 1. Estado actual

### Lo que YA está hecho en el frontend (v1.0.0)

- **178+ módulos**, 75 kB CSS, 550 kB JS, todo navegable.
- **20+ páginas** con su diseño neobrutalista (ligas, equipos, matches, standings, leaderboards, brackets, perfiles, dashboards role-aware).
- **Hooks de datos con contrato estable**: `{ data, isLoading, error }`. El swap mock → real es de **1 línea por hook** (reemplazar `asyncResolve(MOCK_X)` por `apiClient.get(...).then(r => r.data.data)`).
- **Componentes de UI**: 10+ (Button, Card, Chip, Modal, etc.) que se reutilizan en cada pantalla.
- **Catálogo de mocks**: 10 ligas (L1–L10), 30 equipos, 52 usuarios, 20 canchas, 200 partidos, 300 eventos.

### Lo que NO está en el frontend (todo `await`/API stubs en `api/`)

- Endpoints reales para crear/editar/eliminar ligas, equipos, partidos, eventos, memberships.
- POST `/leagues/:id/fixture/generate` (algoritmo de Berger server-side).
- POST `/matches/:id/events` (captura de eventos en live/post).
- PATCH `/matches/:id` (cambiar estado, scores, etc.).
- POST `/leagues/:id/teams` + PATCH (asignar/quitar/reordenar equipos).
- POST `/leagues/:id/teams/:teamId/members` (alta de miembros desde DT).
- POST `/users` + PATCH (admin user management).

### Lo que NO está en el backend

- Modelos Prisma: `Team`, `TeamMembership`, `Match`, `Matchday`, `MatchEvent`, `LeagueTeam`, `Award`, `PlayerSeasonStats`, `TeamSeasonStats`, `KnockoutBracket`.
- Endpoints REST correspondientes.
- Seed determinista que cargue el catálogo de mocks v1.0.0 al primer arranque.

## 4. Fase 3 — Frontend: swap mock → real

**Duración estimada**: 1–2 sesiones (la más rápida de las 3).

### 4.1 Estrategia: incremental por dominio

Orden recomendado (cada paso es mergable independientemente):

1. **Leagues** (el más simple, ya tienes `leaguesApi` real) → wire `useLeague(id)` al API real.
2. **Fields** → wire `useField()` (no existe, se crea) y `useFields()` (no existe).
3. **Users** → `useUserById` consume `/users/:id`.
4. **Teams + Memberships** → `useTeams`, `useTeam`, `useTeamMembers`, `useUserTeams` consumen `/teams` con includes.
5. **League Teams** → `useLeagueTeams`, `useAvailableTeams` consumen `/leagues/:id/teams`.
6. **Matches + Matchdays** → `useMatchdays`, `useMatches`, `useMatch`, `useMatchesByMatchday`.
7. **Events** → `useMatchEvents`, `useMatchEventState`.
8. **Knockout** → `useBracket`.
9. **Standings** → `useStandings` consume `/leagues/:id/standings` (server-computed).
10. **Stats + Highlights** → `useLeagueLeaderboards`, `useLeagueHighlights`, `usePlayerStatsAllLeagues`, `useRefereeStats`.

### 4.2 Patrón de swap (1 línea por hook)

```ts
// Antes (mock):
export function useTeam(teamId: string | null | undefined): AsyncState<Team | null> {
  const key = teamId ?? '__none__';
  const loader = (_k: string) => asyncResolve(teamId ? getTeamById(teamId) : null);
  return useAsync<Team | null>(loader, key);
}

// Después (real):
export function useTeam(teamId: string | null | undefined): AsyncState<Team | null> {
  const key = teamId ?? '__none__';
  const loader = (k: string) =>
    teamId
      ? apiClient.get<SuccessEnvelope<Team>>(`/teams/${teamId}`).then(r => r.data.data)
      : asyncResolve(null);
  return useAsync<Team | null>(loader, key);
}
```

Mismo contrato, misma firma. **Cero cambios en las pantallas**.

## 7. Riesgos & mitigaciones

| Riesgo | Mitigación |
|---|---|
| El seed tarda mucho en correr (1000+ inserts) | Usar `createMany` de Prisma + transacciones; en dev con `prisma db seed --skip-generate` |
| El bundle del frontend se hace más lento con queries reales | Code splitting (Paso 11), React Query para cache, infinite scroll donde aplique |
| Nombres mexicanos mal escritos o mal acento | Usar `faker` con `locale: 'es_MX'`, validar output con regex |
| Las stats computadas en el backend no matchean con las del frontend | Mover `utils/standings.ts` y `utils/playerStats.ts` al backend tal cual (son funciones puras) |
| El usuario quiere cambiar reglas (3 PTS, criterios de desempate) | Parametrizar `pointsForWin` y tiebreakers en `League` table |
| Algunos hooks dependen de datos cruzados (eventos + matches + memberships) | Backend devuelve un payload compuesto (over-fetching OK por simplicidad v1.1) |
| Las pruebas del backend no existen | En v1.1 el seed es la "prueba" — si corre sin errores, la data está OK |
