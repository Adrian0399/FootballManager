### Modelos (11)

| Modelo | Tabla | Propósito | Relaciones clave |

`UserRole`, `TeamRole`, `FieldPosition`, `LeagueFormat`, `LeagueType`,

`EventType`, `ScoringMode`, `KnockoutStage`.

### Convenciones obligatorias (no negociables)

- **4 columnas de auditoría** en toda tabla:
  `created_at`, `created_by`, `updated_at`, `updated_by`.
  (Excepción aceptada: `match_events` solo tiene `created_*`, porque los
  eventos no se editan — ver nota en §1.3.)
- **Soft delete**: toda entidad de dominio tiene `deleted_at` (nullable).
  La única sin `deleted_at` es `MatchEvent` (append-only).
- **IDs**: `UUID` con `gen_random_uuid()`.
- **Nombres de columna**: `snake_case` en DB, `camelCase` en Prisma vía `@map`.
- **Nombres de tabla**: plural, `snake_case` vía `@@map`.

### Índices ya definidos (los importantes)

- `users(email)`, `users(curp)`, `users(role)`, `users(isActive)`, `users(deletedAt)`
- `leagues(format)`, `leagues(status)`, `leagues(matchdaysCount)`, `leagues(deletedAt)`
- `matches(leagueId, matchdayId)`, `matches(homeTeamId)`, `matches(awayTeamId)`,
  `matches(status)`, `matches(scheduledAt)`, `matches(knockoutStage)`
- `match_events(matchId)`, `match_events(userId)`, `match_events(teamId)`, `match_events(type)`
- `team_memberships(userId)`, `team_memberships(membershipRole)`

|---|---|---|
| `TKT — Lunes Libre Varonil` | IN_PROGRESS (4/30 jornadas) | round-robin en curso |

## 1.2 Gaps de base de datos

| # | Gap | Impacto | Prioridad |
|---|---|---|---|
| DB-1 | **No existe modelo `Award`** | El perfil muestra premios mock; no se pueden persistir ni consultar | P1 |
| DB-2 | **No existe estadística agregada de jugador** (`PlayerSeasonStat`) | Stats de jugador por liga se calculan on-the-fly; con 3000 partidos puede ser lento y no permite "premios históricos" | P2 |
| DB-3 | **No hay alineación por partido** (`MatchLineup`) | No se puede registrar quién jugó (solo eventos). Sin esto, "partidos jugados" de un jugador se infiere de eventos (impreciso) | P2 |
| DB-4 | `MatchEvent` no tiene `updated_at/updated_by` | Política deliberada (append-only). Si se permite corregir eventos, hace falta PATCH + auditoría | P2 |
| DB-5 | **No hay tabla de auditoría general** (`AuditLog`) | Cumplimiento/histórico: quién cambió qué y cuándo, más allá de las 4 columnas | P3 |
| DB-6 | No hay `Notification` | Avisos de partidos/resultados | P3 |
| DB-7 | `LeagueTeam.groupLabel` existe pero no hay lógica de grupos en servicios | `LeagueType.GROUPS_KNOCKOUT` no está soportado end-to-end | P2 |

### DB-1 — `Award` (P1, necesario para el perfil)

Representa un reconocimiento histórico (no se recalcula; se "otorga").

```prisma
enum AwardCategory {
  SCORER        // goleador
  MVP           // mejor jugador
  FAIR_PLAY     // juego limpio
  CHAMPION      // campeón
  BEST_DEFENSE  // mejor defensa
}

enum AwardLevel {
  GOLD
  SILVER
  BRONZE
}

model Award {
  id          String        @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  // A quién se le otorga (siempre un usuario).
  userId      String        @map("user_id") @db.Uuid
  // Contexto del premio (opcional: puede ser premio de liga, de equipo o suelto).
  leagueId    String?       @map("league_id") @db.Uuid
  teamId      String?       @map("team_id") @db.Uuid
  category    AwardCategory @map("category")
  level       AwardLevel    @map("level")
  title       String        @db.VarChar(120)   // texto visible, ej. "Bota de Oro Apertura 2025"
  description String?       @db.VarChar(500)
  awardedAt   DateTime      @map("awarded_at") @db.Date

  // ----- Auditoría -----
  createdAt   DateTime  @default(now()) @map("created_at")
  createdById String?   @map("created_by") @db.Uuid
  createdBy   User?     @relation("AwardCreatedBy", fields: [createdById], references: [id], onDelete: SetNull)
  updatedAt   DateTime  @updatedAt @map("updated_at")
  updatedById String?   @map("updated_by") @db.Uuid
  updatedBy   User?     @relation("AwardUpdatedBy", fields: [updatedById], references: [id], onDelete: SetNull)
  deletedAt   DateTime? @map("deleted_at")

  // ----- Relaciones -----
  user   User    @relation("AwardWinner", fields: [userId], references: [id], onDelete: Cascade)
  league League? @relation(fields: [leagueId], references: [id], onDelete: SetNull)
  team   Team?   @relation(fields: [teamId], references: [id], onDelete: SetNull)

  @@index([userId])
  @@index([leagueId])
  @@index([teamId])
  @@index([category])
  @@index([deletedAt])
  @@map("awards")
}
```

> Requiere agregar las relaciones inversas en `User`, `League`, `Team`
> (`awardsWon`, `awards`, `awards`).

**Alternativa sin tabla** (si se quiere evitar migración): derivar premios
de las stats ya calculadas (goleador = top scorer de cada liga FINISHED,
etc.). Menos flexible y no soporta "premios históricos" ni premios manuales.
**Recomendación**: crear la tabla.

# PARTE 2 — ENDPOINTS

## 2.1 Convenciones (resumen de `docs/api.md`)

- Base: `/api/v1`. Versión en el path.
- Envelope obligatorio: `{ success, statusCode, data }` / `{ success:false,
  statusCode, error:{ code, message, issues? } }`.
- Helpers: `ok(res, data)`, `created(res, data)`, `fail(...)`.
- Middlewares: `authenticate` (todos los endpoints salvo auth), `authorize('ADMIN')`
  en mutaciones, `validateBody(zodSchema)`.
- **Regla de rol**: `ADMIN` muta; el resto lee (`docs/api.md §9`).
  Excepción a considerar: árbitro captura eventos de SUS partidos
  (ver Fase B — decisión de producto pendiente).
- Soft delete: `DELETE` marca `deleted_at`; `?includeInactive=true` los lista.
- Paginación `?page=&size=` (aún no implementada en servicios).
